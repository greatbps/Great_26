# 6대 자산 산정모듈 — STORM 연동·BORAME 고도화 심화분석 (USP 반영판)

**분석 범위**: RFP SFR-005~011 원문 전수 재검토
**목적**: ① STORM 출력값 정의 ② 입력 가공·자동화 방안 ③ BORAME 미흡점과 발전방향 ④ USP화

---

## 0. 핵심 발견 — RFP는 입력 소스를 두 그룹으로 이미 구분해 놓았다

RFP 원문을 정확히 대조하면, 6대 자산 절차도의 상단 라벨이 전부 "STORM 모의결과"인 게 아닙니다.

| 자산 | RFP가 명시한 절차도 상단 라벨 |
|---|---|
| 마. 항공기 | **STORM 모의결과** |
| 바. 작전지원장비 | **STORM 모의결과** |
| 아. 탄약 | **STORM 모의결과** |
| 차. 수리부속 | **STORM 모의결과** |
| 사. 인원 | **旣 산출 자료** (STORM이 아니라, 마·바 등에서 이미 계산된 결과!) |
| 자. 유류 | **旣 산출 자료** |
| 카. 물자 | **旣 산출 자료** |

→ 이것이 이번 분석의 핵심 USP입니다: **6대 자산은 병렬 구조가 아니라 "STORM 직접소비 4개 + 선행결과 재소비 3개"의 2계층 캐스케이드(Cascade) 구조**입니다. 이 구조를 정확히 짚어낸 것 자체가 "사업 이해도"에서 경쟁사 대비 USP가 됩니다.

```
STORM ──┬──▶ 마.항공기 ───┬──▶ 사.인원 (임무수행간 항공기 피해 재입력)
        ├──▶ 바.작전지원장비 ─┴──▶ 자.유류 (항공기+부대피해 재입력)
        ├──▶ 아.탄약                    └──▶ 카.물자 (인원+피해현황 재입력)
        └──▶ 차.수리부속
```

## 1. 자산별 STORM/선행자료 출력값 — RFP 원문 그대로 필드 정의

### 마. 항공기 — STORM 직접 소비
STORM 출력: `항공기 손실` · `기종별 전시 임무 및 소티` · `전구급 我 부대 피해(항공침투, TBM 등) 현황`
**+ STORM이 다루지 않는 영역**: STORM 非모의 기종(KC-330 공중기동기, RC-800 감시통제기 등)은 STORM 출력에 없으므로 **별도 계획 임무·소티 입력경로**를 체계 자체에 마련해야 함 — RFP가 명시한 갭

### 바. 작전지원장비 — STORM 직접 소비
STORM 출력: `전구급 我 부대 피해(항공침투, TBM 등) 현황`
**+ DELIIS 연동**: 장비종별 수량 및 최대·최소 수명은 "DELIIS 데이터 자료 업로드"로 명시 → STORM이 아니라 **국방후속군수지원종합정보체계(DELIIS)**가 원천

### 사. 인원 — 旣 산출 자료 소비 (STORM 아님)
입력: `임무 수행 간 항공기 피해`(=마의 산출물) · `我 부대 피해(항공침투, TBM 등) 현황`(=바와 공유하는 STORM 원시값, 특수전부대 피해 포함)
→ 즉 인원 모듈은 **마의 산출 결과를 그대로 물려받는 하류(downstream) 모듈**

### 아. 탄약 — STORM 직접 소비
STORM 출력: `항공기 손실` · `기종별 실시 임무 비율 및 소티` · `항공기 및 무기별 敵 항공기 격추수(율)` · `항공기 기종별 손실률`
**+ KAFARAM 준용**: 위 STORM 원시값을 KAFARAM의 "탄종별 소모량(율) 판단 로직"에 대입해 탄종별(공대공/공대지/일반폭탄/특수목적탄/방공유도탄/기타) 산출

### 자. 유류 — 旣 산출 자료 소비 (STORM 아님)
입력: `我 全기종 전시 임무 및 소티` · `임무 수행 간 항공기 피해`(=마 산출물) · `我 부대 피해 현황`(특수전부대 피해 포함)
→ 유류도 **마의 산출 결과 하류 모듈**

### 차. 수리부속 — STORM 직접 소비
STORM 출력: `항공기 손실(소파/중파/대파 손상등급)` · `기종별 전시 실시 임무 및 소티` · `전구급 我 부대 피해 현황`
**+ DELIIS 연동**: 기지별 창고 내 수리부속 저장 수량, 평시 장비별 연간 수리부속 소모실적 — 둘 다 "DELIIS 데이터 자료 업로드"로 명시

### 카. 물자 — 旣 산출 자료 소비 (STORM 아님)
입력: `我 인원편제(계급별·병과별) 현황`(=사 산출물) · `我 기지별 인원·장비·시설 피해 현황`(항공/TBM/특수전부대 피해 전부 포함, =사·바 산출물 통합)
→ 물자는 **인원(사)·장비(바) 산출물을 동시에 물려받는 최하류 모듈**

## 2. 입력 가공·자동화 방안 (STORM ETL 파이프라인)

RFP가 요구하는 "STORM 분석결과 입력(csv/xml/xls 자동변환)"(SFR-003)을 6대 자산 각각이 재구현하면 비효율적입니다. **STORM 출력을 한 번만 정규화해 6대 자산이 계층적으로 재사용하는 단일 ETL 파이프라인**을 제안합니다.

```
[1단계] STORM 원본 수신
  csv/xml/xls 포맷 자동 감지 → 원본 그대로 스테이징 테이블 적재(TBL_STORM_RAW)

[2단계] 표준 스키마 정규화 (자동변환 규칙엔진)
  필드 매핑 테이블(TBL_STORM_MAPPING: STORM필드명 → 목표체계 표준필드명)을 참조해
  "항공기손실코드/기종ID/일자/원인코드/소티수/격추수" 등 표준 필드셋으로 변환
  → TBL_STORM_NORMALIZED (6대 자산이 공유하는 단일 정규화 테이블)

[3단계] 무결성 검증 (DAR-002/004 요구사항과 연계)
  - 결측값·이상치 자동 탐지(통계적 이상치 탐지, 이전 답변의 AI/빅데이터 1순위 항목과 연결)
  - 검증 실패 레코드는 오류메시지와 함께 격리테이블(TBL_STORM_ERROR)로 분리

[4단계] 계층적 라우팅 (자동화의 핵심)
  1차 소비군(마·바·아·차)이 TBL_STORM_NORMALIZED를 직접 구독(Subscribe)
  1차 소비군의 산출 완료 시점에 완료 이벤트(Event) 발행
  2차 소비군(사·자·카)은 이벤트를 트리거로 자동 재계산 실행
  → 사람이 "인원 계산 눌러야지" 수동 트리거할 필요 없이, 마의 산출이 끝나는 순간 사·자가 자동 연쇄 실행

[5단계] DELIIS 연동 배치
  DELIIS 자료(장비수량·수명, 수리부속 저장수량·소모실적)는 STORM과 별도 배치로 주기 수신
  → TBL_DELIIS_SYNC(동기화일시, 자료유형, 상태) 로 최신성 관리
```

**자동화 구현 포인트(설계 및 구현방안 페이지에 넣을 문구)**
- "6대 자산 모듈이 각자 STORM 파서를 만드는 대신, 정규화 계층을 1회 구축해 재사용 — 개발 리스크·유지보수 비용 동시 절감"
- "1차 소비군 산출 완료 → 이벤트 기반 자동 트리거로 2차 소비군 실행 — 수작업 순번 관리 불필요"

## 3. 자산별 BORAME 미흡점 진단 → 발전방안

| 자산 | BORAME 현재 수준 | 미흡점(Gap) | 목표체계 발전방안 |
|---|---|---|---|
| **마.항공기** | 시뮬레이션 중 상태전이(FMC/NMC/ABDR/Kill)만 판정 | ① STORM 결과를 배치로 받아 "소요산정"하는 절차 자체가 없음 ② 敵공격 형태별(공대공/지대공/특수전) 구분 손실 미제공 ③ STORM 非모의 기종(KC-330 등) 처리 로직 없음 | STORM 소요산정 절차 신규 구축 + 격추비(7:3, 9:1 등) 파라미터화 + 非모의기종 별도 입력경로 추가 |
| **바.작전지원장비** | 등가원 피해모형·강화시설 면역 로직 보유(BORAME 최강점) | ① 피해율(%)까지만 계산, "소요산정"(시간 경과에 따른 보충량)으로 미확장 ② 기능별(대공방어/정비/통신 등) 세분화 없음 ③ DELIIS 연동 없음(수기 입력 전제) | 피해율 → 보충소요량 환산 로직 추가 + 기능별 분류체계 신설 + DELIIS 자동연동 |
| **사.인원** | **모델 자체가 없음(완전 공백)** | 인명피해 개념 자체가 BORAME 설계범위 밖 | 시설피해율×배치인원 기대손실모형 신규개발, 특수임무인력(TACP·CCT·항공구조사) 별도 손실률 반영 |
| **아.탄약** | BORAME 범위 아님(KAFARAM 소관) | KAFARAM은 "소모량(율) 판단"까지만, "확보·비축 목표"·"前연구 대비 비교결과표"·"3군 공통탄약" 통합 뷰가 없음 | KAFARAM 산출값 위에 확보/비축 계층 추가 + 前연구 비교 트레이서빌리티 기능 신규 |
| **자.유류** | **모델 자체가 없음(완전 공백)** | BORAME·KAFARAM 어디에도 유류 개념 없음 | 소티기반 소모식 완전 신규개발(§자원분석모델_수리모형_설계안.md §3.5 참조) |
| **차.수리부속** | 고장확률·K-Factor 입력체계 보유(BORAME 2번째 강점) | ① 항공기 부속 중심 설계, "항공기 외 장비" 확장 미흡 ② DELIIS 저장수량·소모실적 자동연동 없음(수기) ③ 손실/손상 교환비(1:1.4 등) 개념 없음 | 항공기 외 장비 대상 확장 + DELIIS 자동연동 + 교환비 파라미터 신규 반영 |
| **카.물자** | **모델 자체가 없음(완전 공백)** | 1~8종 물자 분류·산정논리 자체가 BORAME 범위 밖 | RFP가 예시로 제시한 산정논리를 그대로 구현(§4 참조) |

**패턴 요약**: BORAME은 "시설·항공기·수리부속"이라는 **물적자산(hardware) 피해판정**에는 강하지만, "소요산정"(시계열 보충량 계산)·"인원"·"유류"·"물자"·"외부체계 연동(DELIIS)"에는 전무합니다. 이게 바로 이 사업이 "BORAME 유지보수"가 아니라 "**BORAME를 계승한 신규 자원분석모델 개발**"이어야 하는 이유이자, 제안서에서 강조해야 할 지점입니다.

## 4. 물자(카) 산정논리 — RFP가 직접 제시한 예시 그대로 반영 (수정 없이 인용)

RFP는 물자소요산정에 한해 이례적으로 **구체적 산정 공식 예시**를 제공합니다. 이를 그대로 설계에 반영합니다.

```
[1종 식량류 - 전투식량]
소요량 = (비축소요인가기준 ÷ 6일 × 전시단계별 운영일수) + (창고별 저장량 × 창고피해율)

[2종 피복 - 개인피복]
소요량 = Σ(편제인원 × 재보급기준 ÷ 365일) + Σ(일별 인원피해 × 피해기준) + (창고별 저장량 × 창고피해율)

※ 같은 2종이라도 특수피복 중 "병과피복"과 "환자피복"은 산정논리를 별도 구분 적용
  (환자피복은 인원피해 발생량에 연동, 병과피복은 편제인원 재보급주기에 연동 — 서로 다른 트리거)
```

**설계 반영**: 대구분(1~8종)-중구분-소구분-대상품목 4단계 분류체계를 `TBL_SUPPLY_CLASSIFY`로 구현하고, 소구분 단위마다 산정논리 코드(`CALC_LOGIC_ID`)를 매핑해 **품목별로 다른 계산식이 자동 선택되도록** 설계 — 이게 이전 스토리보드의 `TBL_ITEM_GROUP_MAP`을 한 단계 구체화한 것입니다.

## 5. USP 종합 문구 (제안서 삽입용)

> "본 목표체계는 STORM 출력을 6대 자산이 병렬로 나눠 갖는 방식이 아니라, **STORM 직접소비 4개 자산(항공기·작전지원장비·탄약·수리부속)과 선행결과 재소비 3개 자산(인원·유류·물자)의 2계층 캐스케이드 구조**로 정확히 설계했다. 이는 RFP가 절차도 상단에 'STORM 모의결과'와 '旣 산출 자료'를 구분 명기한 것을 정밀 분석한 결과이며, 단일 정규화 ETL과 이벤트 기반 자동 재계산으로 구현해 개발 리스크와 유지보수 비용을 동시에 낮춘다.
>
> 또한 BORAME이 강한 영역(시설·항공기·수리부속의 물적피해 판정)은 그대로 계승하되, BORAME이 전혀 다루지 않는 인원·유류·물자·DELIIS 연동은 완전 신규 개발하여 '기존 검증된 로직 재사용'과 '신뢰성 있는 신규 개발'을 사업 전체에서 명확히 구분·병행한다."

이 문구는 Ⅱ-3(적용기술), Ⅱ-2 ADVANCED Strategy의 [E] Enhanced Legacy Integration / [A] Automated STORM Interfacing 두 전략 설명에 그대로 삽입 가능합니다.

## 6. 기존 스토리보드 대비 개정이 필요한 페이지

| 기존 페이지 | 개정 방향 |
|---|---|
| 마-2), 바-2), 아-1)~2), 차-1)~2) | "STORM 직접소비" 명시 + STORM 출력 필드명 원문 그대로 표기 |
