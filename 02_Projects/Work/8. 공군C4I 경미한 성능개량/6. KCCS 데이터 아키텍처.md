기존 C4I:

시스템 A ↔ 시스템 B ↔ 시스템 C  
(각자 따로 놀음)

---

KCCS 구조:

모든 시스템 → 데이터 플랫폼 → 모든 시스템

👉 핵심:

- 시스템이 아니라 **데이터가 중심**

---

# 🧠 2. 전체 구조 (제안서용 핵심 아키텍처)

[각 군 C4I / 무기체계 / 센서]  
        ↓  
[Adapter Layer (표준 변환)]  
        ↓  
[Data Ingestion Layer]  
        ↓  
[Message Broker / Event Bus]  
        ↓  
[통합 데이터 모델 (Canonical Model)]  
        ↓  
[Data Lake / Operational DB]  
        ↓  
[API Gateway / Data Service Layer]  
        ↓  
[AFCCS / KCCS / 타 체계]

---

# 🏗️ 3. 레이어별 핵심 설명 (평가 포인트)

## ① Adapter Layer (진짜 중요 ⭐)

역할:

- 각 체계 데이터 변환

왜 중요?

- 40개 체계 → 포맷 다름

👉 핵심 문장:

> 이기종 체계 간 데이터 상호운용성을 확보하기 위한 표준 변환 계층

---

## ② Data Ingestion Layer

- 실시간 데이터 수집
- 스트리밍 처리

👉 기술:

- Kafka / MQ 계열

---

## ③ Message Broker / Event Bus ⭐⭐⭐

핵심:

> ❗ KCCS의 심장

역할:

- 데이터 흐름 통제
- 비동기 처리

---

## ④ Canonical Data Model (핵심 중 핵심)

이거 없으면 KCCS 안 된다.

👉 정의:

> 모든 데이터를 공통 형식으로 정의한 표준 모델

---

예:

Target  
Track  
Mission  
Unit  
Event

---

👉 핵심 문장:

> 데이터 중심 아키텍처 구현을 위해 공통 데이터 모델 정의 필수

---

## ⑤ Data Storage

2개로 나눠야 한다:

### ✔ Operational DB

- 실시간 처리

### ✔ Data Lake

- 분석 / AI

---

## ⑥ API Gateway / Data Service Layer

역할:

- 데이터 제공
- 시스템 연결

👉 핵심:

> 시스템 간 직접 연결 금지 → API로만 접근

---

# 🔗 4. JADC2까지 연결되는 이유

이 구조가 중요한 이유:

👉 그대로 확장하면:

- KCCS → 합동 데이터 공유
- JADC2 → 전 영역 연결

---

👉 핵심 문장:

> 본 구조는 향후 JADC2 환경에서 요구되는 데이터 중심 상호운용성을 자연스럽게 지원함

---

# ⚔️ 5. 아이티센엔텍과 차별화 포인트

## 🔴 기존 방식

시스템 ↔ 시스템 직접 연결  
(Point-to-Point)

문제:

- 확장 불가
- 복잡도 폭발

---

## 🔵 우리가 제안하는 방식

시스템 → 데이터 플랫폼 → 시스템

👉 차이:

|항목|기존|제안|
|---|---|---|
|구조|폐쇄형|개방형|
|확장성|낮음|높음|
|유지보수|어려움|용이|
|JADC2 대응|불가|가능|

---

# 💣 6. 평가위원 먹히는 문장 (그대로 써라)

### 핵심 문장 1

> 데이터 중심 아키텍처를 기반으로 이기종 체계 간 상호운용성을 확보하고, 향후 KCCS 및 JADC2 확장을 고려한 구조로 설계

---

### 핵심 문장 2

> 기존 시스템 간 직접 연동 방식에서 탈피하여, 메시지 기반 비동기 구조를 적용함으로써 확장성과 안정성을 확보

---

### 핵심 문장 3

> 공통 데이터 모델을 정의하여 데이터 표준화를 구현하고, 체계 간 데이터 정합성을 보장

---

# 🎯 7. 한 방 정리 (면접/설명회용)

> 👉 데이터를 표준화해서 공유하는 구조입니다”
